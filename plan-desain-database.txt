| Rancangan sebelumnya | Penyederhanaan |
|---|---|
| `roles` dan `user_roles` | Menjadi kolom `users.role`, dengan asumsi satu role per akun |

| `analysis_metrics` | Kolom numerik utama langsung pada `analysis_runs` |
| `analysis_artifacts` | File keluaran dicatat pada `media_assets` dan dihubungkan ke run |
| `clinical_approvals` | Kolom persetujuan pada setiap versi `reports` |

Untuk persetujuan, asumsi awalnya **satu persetujuan dokter per versi laporan**, dan laporan menunjuk revisi hasil yang disetujui. Jika nanti dibutuhkan banyak penandatangan atau beberapa tahap persetujuan, barulah tabel persetujuan terpisah diperlukan.

JSON tetap boleh dipakai untuk **snapshot konfigurasi dan detail tambahan**, tetapi hubungan penting seperti pasien → pemeriksaan → analisis tetap menggunakan foreign key.

**5. Mengapa Beberapa Tabel Tetap Dipisahkan?**

Tiga bagian ini sebaiknya tidak dipaksakan menjadi satu:

- **`analysis_runs`:** hasil dari satu eksekusi AI terhadap media tertentu.
- **`analysis_revisions`:** versi hasil yang ditinjau manusia, termasuk hasil dari beberapa video.
- **`reports`:** dokumen berdasarkan revisi yang telah disetujui.

Contohnya:

```text
Video dianalisis → hasil AI asli
                         ↓
Analis mengoreksi → revisi hasil baru
                         ↓
Dokter menyetujui → laporan dirilis
```

Dengan pemisahan tersebut, hasil asli tidak hilang ketika dikoreksi, dan laporan tidak berubah hanya karena video dianalisis ulang. Ini mengikuti kebutuhan pada `PRD.md:278` dan `CLAUDE.md:58`.

`review_events` juga tetap dipisahkan dari `audit_logs`: koreksi hasil adalah data bisnis yang perlu ditinjau, sedangkan audit mencatat aktivitas sistem secara lebih luas.

**6. Batas Penyederhanaannya**

Walaupun tabel dikurangi, kebutuhan berikut tetap dipertahankan:
- Lima role dan pemeriksaan akses di backend.
- Hasil per-video tetap terpisah dari hasil gabungan.
- Snapshot kalibrasi yang digunakan tidak ikut berubah ketika profil diedit.
- Koreksi menghasilkan revisi; hasil asli tetap tersedia.
- Laporan yang sudah disetujui tidak boleh diam-diam diganti.
- Pasien hanya mengakses laporan miliknya yang sudah dirilis.
- ID integer yang berurutan **bukan pengaman akses**; kepemilikan record tetap diperiksa oleh backend.

**Rekomendasi akhir saya: satu file SQLite, ID integer, lima role, dan 12 tabel awal.** Ini lebih seimbang daripada rancangan 19 tabel: cukup sederhana untuk dikerjakan, tetapi tetap menjaga alur review, persetujuan, dan keterlacakan yang diminta dokumen.

## TABEL 12: audit_logs
==============================================================================
Menyimpan audit trail untuk semua sensitive system actions

CREATE TABLE audit_logs (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,

    -- Actor identification
    actor_id            INTEGER REFERENCES users(id) ON DELETE SET NULL,
    actor_email         TEXT,                   -- snapshot email saat event
    actor_role          TEXT,                   -- snapshot role saat event
    actor_ip            TEXT,

    -- Action details
    action_type         TEXT NOT NULL,          -- LOGIN | LOGOUT | CREATE_PATIENT | UPLOAD_VIDEO | RUN_ANALYSIS | SUBMIT_REVIEW | APPROVE_REPORT | RELEASE_REPORT | DELETE_USER | CHANGE_ROLE | etc.

    target_type         TEXT,                   -- PATIENT | EXAMINATION | MEDIA | ANALYSIS | REVISION | REPORT | USER | CALIBRATION
    target_id           INTEGER,                -- ID dari target resource

    description         TEXT NOT NULL,          -- human-readable description

    -- Before/after snapshot (untuk sensitive changes)
    before_state        TEXT,                   -- JSON snapshot before
    after_state         TEXT,                   -- JSON snapshot after

    -- Result
    result              TEXT NOT NULL           -- SUCCESS | FAILURE | UNAUTHORIZED
                        CHECK(result IN ('SUCCESS', 'FAILURE', 'UNAUTHORIZED')),
    error_message       TEXT,

    -- Timestamp
    created_at          TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_audit_actor ON audit_logs(actor_id);
CREATE INDEX idx_audit_action ON audit_logs(action_type);
CREATE INDEX idx_audit_target ON audit_logs(target_type, target_id);
CREATE INDEX idx_audit_result ON audit_logs(result);
CREATE INDEX idx_audit_created ON audit_logs(created_at);

-- Notes:
-- * Comprehensive audit trail untuk security dan compliance
-- * Snapshot email/role untuk historical accuracy
-- * Before/after state untuk sensitive changes
-- * Protected: ordinary users CANNOT modify audit_logs

## Key Design Decisions
==============================================================================

1. **Integer IDs instead of UUIDs**
   - Simpler untuk development dan debugging
   - AUTHORIZATION masih enforced di application layer
   - Sequential IDs BUKAN security boundary

2. **Inline Macroscopic Data**
   - Disimpan langsung di `examinations` table
   - Tidak perlu tabel terpisah untuk simplicity

3. **Calibration Snapshots as JSON**
   - Immutable copy di `analysis_runs.calibration_snapshot`
   - Preserve reproducibility walau profile berubah

4. **Revision Versioning**
   - Support reanalysis dengan `revision_number`
   - Original AI output preserved di `analysis_runs`

5. **Report Immutability**
   - Released reports READ-ONLY
   - Amendments create new version

6. **Comprehensive Audit Trail**
   - `review_events`: business-level corrections
   - `audit_logs`: system-wide security events
